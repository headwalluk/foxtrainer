# Security model

What foxtrainer reads, writes, downloads and verifies, for anyone deciding whether to trust it
with their browser profiles. Internals are in [Architecture](architecture.md).

## Privileges

- foxtrainer runs as you and never asks for root or administrator rights.
- It writes only to your Firefox profile folders and its own config, cache and state folders
  (`foxtrainer paths` lists them). It never writes to Firefox's install folder or uses
  system-wide policies.
- It reads system folders only to find Firefox installs, hunspell dictionaries and
  system-wide extensions.

## What it changes in a profile

- `user.js`: fully generated by foxtrainer. Written atomically with owner-only permissions (0600).
  A symlinked `user.js` is never replaced.
- `prefs.js`: only entries that foxtrainer itself set earlier, as recorded in its per-instance
  manifest, are removed. Nothing else is changed, and the file keeps its permissions.
- Both files are copied to foxtrainer's state folder before every write, keeping the last 10
  backups per instance.

It never changes `profiles.ini`, `installs.ini` or a Profile Group's shared store, and never
writes `browser.profiles.*` or `toolkit.profiles.*` prefs; the catalogue checker rejects them.
It never reads or changes bookmarks, history, passwords, cookies or other browsing data.

foxtrainer's own files (answers, manifests, backups and cached upstream files) are written with
owner-only permissions.

## Concurrency

foxtrainer will not modify a profile that Firefox is using. It takes Firefox's own profile lock
(a POSIX `fcntl` lock on `.parentlock`) for the duration of an apply, so Firefox cannot start on
that profile part-way through. `diff` and `apply --dry-run` only read, so they work while
Firefox is running.

## Upstream files

foxtrainer reads upstream pref values (from Betterfox) out of the upstream project's own files.
Those files are pinned in the catalogue, which is compiled into the binary:

- Each source is pinned by a **full 40-character git commit SHA**, and each file by its
  **sha256**. foxtrainer never fetches a branch or "latest". Moving a pin is a reviewed catalogue
  change in a foxtrainer release, and the catalogue checker fails until every new upstream pref
  has been placed in a group or excluded with a reason.
- Files are downloaded over HTTPS from `raw.githubusercontent.com` at the pinned commit, and
  verified against the sha256 before use. A mismatch is an error, never a warning, and a file
  that fails the check is never cached.
- Cached copies (in `sources/<source>/<commit>/` under the cache folder) are re-verified before
  every use, so `apply` runs offline from the last verified copy. `--offline` forbids downloads
  altogether.
- Upstream content only ever becomes pref values. Each value is validated as a bool, 32-bit int
  or string, and escaped when `user.js` is written.

## Network

- The upstream files above are the only network requests foxtrainer makes.
- No telemetry. foxtrainer sends nothing about you or your browser anywhere.

## Releases

Release binaries are built by GitHub Actions from a tag (`.github/workflows/release.yml`), with
a `SHA256SUMS` file. `install.sh` refuses to install a download whose checksum doesn't match.
To read exactly what you run, build it yourself: see [Compiling from source](compiling.md).
